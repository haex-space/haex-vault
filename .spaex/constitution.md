- Treat TypeScript’s strict mode as the baseline for new or actively maintained TypeScript code. _[from `com.github.haexmas.atoms.coding-guideline-javascript-typescript/javascript-typescript`]_
- Use `===`/`!==`, `??`, and `?.` deliberately. _[from `com.github.haexmas.atoms.coding-guideline-javascript-typescript/javascript-typescript`]_
- Preserve error causes when translating or re-raising errors — add useful context at the boundary and use exception chaining rather than discarding the original cause. _[from `com.github.haexmas.atoms.coding-guideline-javascript-typescript/javascript-typescript`, `com.github.haexmas.atoms.coding-guideline-python/python`]_
- Use the project’s configured formatter, linter, type checker or compiler, and test runner instead of introducing competing or personal project-wide tooling, and make sure changes pass them — formatting, linting, type-checking, and the relevant tests (e.g. `tsc --noEmit` for TypeScript, or `python -m compileall` plus the configured test and static-check commands when no project-specific commands exist) — before handing off the change. _[from `com.github.haexmas.atoms.coding-guideline-javascript-typescript/javascript-typescript`, `com.github.haexmas.atoms.coding-guideline-python/python`]_
- Validate data at trust boundaries (HTTP responses, request bodies, files, environment variables, message queues, browser storage, and other external input) by parsing or validating it once and passing the resulting domain type inward, so internal code can rely on its stated types and invariants instead of repeatedly defending against every possible input — a TypeScript type assertion has no runtime effect and does not by itself make the data safe. _[from `com.github.haexmas.atoms.coding-guideline-javascript-typescript/javascript-typescript`, `com.github.haexmas.atoms.coding-guideline-python/python`]_
- Await every promise that affects the assertion, and use `Promise.all` or `Promise.allSettled` when the test intentionally exercises concurrent work and its failure semantics. _[from `com.github.haexmas.atoms.coding-guideline-javascript-typescript/javascript-typescript-testing`]_
- For TypeScript, keep type-level tests separate from runtime tests when the project needs to verify inference, assignability, or declaration output, since runtime tests cannot prove a compile-time contract and the compiler cannot prove runtime validation of external data. _[from `com.github.haexmas.atoms.coding-guideline-javascript-typescript/javascript-typescript-testing`]_
- Prefer a small number of clear assertions per scenario over a large fixture that hides what the test is proving, and name tests after the behavior and relevant condition rather than the implementation method name alone. _[from `com.github.haexmas.atoms.coding-guideline-javascript-typescript/javascript-typescript-testing`]_
- Choose the narrowest test level that proves the behavior — unit tests for pure logic and isolated components, integration tests for module boundaries and persistence, and end-to-end tests only for critical user journeys or workflows that need the complete system — and keep the test level visible in the test’s location and name per the repository’s convention. _[from `com.github.haexmas.atoms.coding-guideline-javascript-typescript/javascript-typescript-testing`, `com.github.haexmas.atoms.coding-guideline-python/python-testing`]_
- Exercise both successful and failure behavior — including malformed input, missing values or configuration, rejected promises or expected exceptions, cancellation or timeout behavior, authorization decisions, and persistence failures or resource cleanup — wherever they matter, asserting the exception type and meaningful details without over-specifying incidental message formatting. _[from `com.github.haexmas.atoms.coding-guideline-javascript-typescript/javascript-typescript-testing`, `com.github.haexmas.atoms.coding-guideline-python/python-testing`]_
- Keep mocks narrow and behavior-oriented, mocking an external boundary when isolation or determinism requires it. _[from `com.github.haexmas.atoms.coding-guideline-javascript-typescript/javascript-typescript-testing`, `com.github.haexmas.atoms.coding-guideline-python/python-testing`]_
- Keep tests deterministic and isolated, controlling time, randomness, environment, and external clients or dependencies at explicit boundaries — e.g. temporary directories, controlled clocks, seeded randomness, and explicit fakes or mocks. _[from `com.github.haexmas.atoms.coding-guideline-javascript-typescript/javascript-typescript-testing`, `com.github.haexmas.atoms.coding-guideline-python/python-testing`]_
- Test observable behavior and public contracts, not the exact arrangement of private functions, methods, or other implementation details, so a refactor preserving the contract does not require rewriting the tests. _[from `com.github.haexmas.atoms.coding-guideline-javascript-typescript/javascript-typescript-testing`, `com.github.haexmas.atoms.coding-guideline-python/python-testing`]_
- Use the repository’s configured test runner, environment, formatter, linter, and compiler or static checks; a change should include relevant tests and pass the project’s normal test and static-check commands. _[from `com.github.haexmas.atoms.coding-guideline-javascript-typescript/javascript-typescript-testing`, `com.github.haexmas.atoms.coding-guideline-python/python-testing`]_
- Add type hints to public functions, methods, and meaningful data structures; prefer precise types and protocols over `Any` (using `Any` only at a deliberate untyped boundary, narrowed before it reaches domain logic), prefer modern built-in generics such as `list[str]`/`dict[str, int]` for supported Python versions, and use abstract collection types such as `Mapping` for read-only inputs when they describe the contract better. _[from `com.github.haexmas.atoms.coding-guideline-python/python`]_
- At an application’s top-level entry point, use `asyncio.run()`; library code or code already inside an event loop should expose or await a coroutine instead of starting a nested event loop. _[from `com.github.haexmas.atoms.coding-guideline-python/python`]_
- For distributable projects, use `pyproject.toml` for build-system metadata, project metadata, dependencies, and tool configuration, keeping the declared Python version and dependency constraints explicit and using the project’s chosen environment or lock workflow consistently. _[from `com.github.haexmas.atoms.coding-guideline-python/python`]_
- Keep async code non-blocking, using an appropriate async API or explicitly moving blocking or CPU-heavy work to a worker instead of calling it directly from an event loop. _[from `com.github.haexmas.atoms.coding-guideline-python/python`]_
- Model data explicitly, using a small `dataclass`, `Enum`, or dedicated value object when a concept has invariants. _[from `com.github.haexmas.atoms.coding-guideline-python/python`]_
- Prefer simple, readable control flow: use comprehensions for small transformations and a normal loop when conditions, side effects, or error handling would make a comprehension difficult to read. _[from `com.github.haexmas.atoms.coding-guideline-python/python`]_
- Prefer the standard library and existing project dependencies before adding a new package, and keep dependency additions justified by a real capability or maintenance benefit rather than a shorter one-off expression. _[from `com.github.haexmas.atoms.coding-guideline-python/python`]_
- Raise specific exceptions and catch only exceptions that can be handled at that layer. _[from `com.github.haexmas.atoms.coding-guideline-python/python`]_
- Use context managers for resources such as files, locks, and transactions. _[from `com.github.haexmas.atoms.coding-guideline-python/python`]_
- For async code, test coroutines with the project’s supported async test tooling, and test cancellation, timeout, cleanup, and ordering assumptions when they affect correctness. _[from `com.github.haexmas.atoms.coding-guideline-python/python-testing`]_
- Keep parametrized test cases focused and readable; add a new case when it demonstrates a distinct boundary or regression, rather than hiding unrelated scenarios inside a large fixture or broad parameter matrix. _[from `com.github.haexmas.atoms.coding-guideline-python/python-testing`]_
- Keep tests easy to read, fast enough to run frequently, and honest about what they do not cover — a passing test is evidence only for the behavior it actually exercises. _[from `com.github.haexmas.atoms.coding-guideline-python/python-testing`]_
- Use `unittest` or the project’s chosen test framework consistently, with fixtures that make setup and cleanup explicit — using context managers and framework cleanup hooks so a failing test cannot leak files, connections, processes, or patches into the next test. _[from `com.github.haexmas.atoms.coding-guideline-python/python-testing`]_
- Prefer iterators and combinators when they make the transformation clearer, but use an ordinary loop when it communicates control flow or error handling better; idiomatic syntax is not a reason to make code harder to read. _[from `com.github.haexmas.atoms.coding-guideline-rust/rust`]_
- Prefer types that make invalid states unrepresentable, using enums for a closed set of states and `Option<T>` for an explicitly optional value rather than encoding either as sentinel values or loosely related booleans. _[from `com.github.haexmas.atoms.coding-guideline-rust/rust`]_
- Prefer explicit assertions with useful failure context; avoid weakening a production invariant merely to make a test convenient, and make the fixture satisfy the same contract as a real caller. _[from `com.github.haexmas.atoms.coding-guideline-rust/rust-testing`]_
- A file should have one primary reason to change; split a file when it has unrelated responsibilities, independent public concepts, different change owners, or tests that are difficult to isolate, not solely to make files shorter. _[from `com.github.haexmas.atoms.general-coding/general-coding`]_
- Comments should explain why a non-obvious decision exists, what invariant must be preserved, or which external constraint applies, not narrate code that could be made clear through structure and naming; update comments when the behavior changes. _[from `com.github.haexmas.atoms.general-coding/general-coding`]_
- Prefer a change that clearly improves maintainability and correctness over theoretical perfection; when a design is uncertain, make the smallest reversible change that provides evidence about the next decision. _[from `com.github.haexmas.atoms.general-coding/general-coding`]_
- Prefer early returns or named helpers when they make the main path easier to follow, reducing nesting without scattering one simple operation across many microscopic functions. _[from `com.github.haexmas.atoms.general-coding/general-coding`]_
- Refactor repeated behavior when the shared rule is real and the abstraction makes both callers clearer, keeping the abstraction close to the domain that owns it and avoiding a generic utility module becoming a dumping ground. _[from `com.github.haexmas.atoms.general-coding/general-coding`]_
- Separate broad formatting or mechanical refactors from behavior changes when possible, since mixed diffs make review, debugging, rollback, and blame less reliable. _[from `com.github.haexmas.atoms.general-coding/general-coding`]_
- Treat a change of about 100 net lines as a useful review-size warning and a change approaching 1000 lines as a strong prompt to split the work or agree on the larger change in advance; identify generated code, mechanical renames, and required migrations as legitimate exceptions. _[from `com.github.haexmas.atoms.general-coding/general-coding`]_
- Use smaller soft thresholds as prompts for review, not as automatic failures: a function or method beyond roughly 40–60 lines, or nesting deeper than roughly three levels, deserves a deliberate look at whether it is still one coherent unit or has distinct responsibilities to name and separate. _[from `com.github.haexmas.atoms.general-coding/general-coding`]_
- For any codebase question, such as what something does, where it lives, how pieces relate, whether an existing artifact already satisfies a request, or tracing a symptom to its source, including exploratory lookups incidental to a larger task, run a graphify context-map query before a raw grep/rg search or broad file reads: state the intent as a question, choose a token budget starting around 800–1500 tokens, run `graphify query "<intent>" --budget <N>` or `graphify path`/`graphify explain` for one specific relationship, then read only the smallest source slices the result points to; the only exemption is a local one-file edit at a symbol whose location is already known from earlier in the same task. _[from `com.github.haexmas.atoms.graphify-first-authoring/graphify-context-map`]_
- Preserve in the resulting context map, when available, the task intent and token budget, the selected files and symbols, the relevant edge or call relationship, source locations for every claim, and an explicit truncation or failed-consultation note. _[from `com.github.haexmas.atoms.graphify-first-authoring/graphify-context-map`]_
- Use rough thresholds, not hard cutoffs, when interpreting graph output and self-detection signals as prompts to consult the graph: extract and propose a refactor at roughly six or more identical lines of shared logic; treat a near-duplicate name, a third similar utility, ten-plus adapted lines, or the thought “similar but different enough” as a signal to consult rather than as a decision; and leave purely structural duplication under about five lines, or duplication inside test files other than helper functions, alone, since operator judgment overrides these thresholds. _[from `com.github.haexmas.atoms.graphify-first-authoring/graphify-first-authoring`]_
- Run frontend and script commands through the devShell, such as `nix develop --command pnpm <script>` for `pnpm exec prettier --write`, `pnpm lint`, and `pnpm typecheck`, and run cargo through `nix develop --command scripts/with-nix-host-bridge.sh cargo <args>` rather than a plain `nix develop --command cargo ...`, which fails in the GTK/WebKit sys crates. _[from `com.github.haexmas.atoms.holzi/holzi-devshell-commands`]_
- Run `nix develop --command pnpm install --frozen-lockfile` in a fresh worktree before using `pnpm exec` there. _[from `com.github.haexmas.atoms.holzi/holzi-devshell-commands`]_
- Run `pnpm exec prettier --write` on every Markdown or JSON file a change touches, including files under `specs/` and `docs/`, before committing, since `pnpm format:check` is a CI check. _[from `com.github.haexmas.atoms.holzi/holzi-devshell-commands`]_
- When a command fails with `node: not found`, `tauri: not found`, or a GTK/WebKit linker error, first check whether it ran through `nix develop --command`, where `IN_NIX_SHELL` is set, before looking for another cause. _[from `com.github.haexmas.atoms.holzi/holzi-devshell-commands`]_
- Climb the YAGNI ladder before writing code, but only after reading the task and the code it touches and tracing the real flow end to end: check whether this needs to be built at all, whether it already exists in the codebase, whether the standard library already does it, whether a native platform feature covers it, whether an already-installed dependency solves it, whether it can be one line, and only then write the minimum code that works. _[from `com.github.haexmas.atoms.ponytail/ponytail`]_
- Fix the root cause in the shared function itself rather than patching only the caller a bug report names, by grepping every caller of the function being touched first. _[from `com.github.haexmas.atoms.ponytail/ponytail`]_

## SHOULD_NOT

- Do not install a package automatically, and do not make adoption of this molecule fail solely because the optional tool is absent. _[from `com.github.haexmas.atoms.ast-grep/ast-grep-structural-search`]_
- For rewrites, do not apply a blanket change merely because the pattern matches; review the complete match set and run the relevant tests first. _[from `com.github.haexmas.atoms.ast-grep/ast-grep-structural-search`]_
- Avoid `any`; use a precise type, a generic, or `unknown` followed by explicit narrowing, and keep any necessary untyped escape hatches local with an explanation of why they are needed. _[from `com.github.haexmas.atoms.coding-guideline-javascript-typescript/javascript-typescript`]_
- Do not assume that a platform-specific global or API exists everywhere, since browser, Node.js, and serverless environments have different APIs and failure modes. _[from `com.github.haexmas.atoms.coding-guideline-javascript-typescript/javascript-typescript`]_
- Do not catch an error merely to log and rethrow it unchanged, since that usually duplicates logs and loses ownership of the failure decision. _[from `com.github.haexmas.atoms.coding-guideline-javascript-typescript/javascript-typescript`]_
- Do not introduce a barrel export or a new abstraction only to shorten an import path. _[from `com.github.haexmas.atoms.coding-guideline-javascript-typescript/javascript-typescript`]_
- Do not leave promises unhandled. _[from `com.github.haexmas.atoms.coding-guideline-javascript-typescript/javascript-typescript`]_
- Do not use `||` when a valid falsy value such as `0`, `false`, or `""` must be preserved, and do not hide a required value behind optional chaining without deciding how its absence is handled. _[from `com.github.haexmas.atoms.coding-guideline-javascript-typescript/javascript-typescript`]_
- Do not use mutation or shared mutable module state as an accidental communication channel. _[from `com.github.haexmas.atoms.coding-guideline-javascript-typescript/javascript-typescript`]_
- Do not leave floating promises in tests, and do not let a test pass before the asynchronous work it is meant to verify has completed. _[from `com.github.haexmas.atoms.coding-guideline-javascript-typescript/javascript-typescript-testing`]_
- Do not turn every test into a slow end-to-end test. _[from `com.github.haexmas.atoms.coding-guideline-javascript-typescript/javascript-typescript-testing`]_
- Avoid real network calls or services, shared mutable module state, order dependence, random values without a controlled seed, and arbitrary timer sleeps in tests. _[from `com.github.haexmas.atoms.coding-guideline-javascript-typescript/javascript-typescript-testing`, `com.github.haexmas.atoms.coding-guideline-python/python-testing`]_
- Do not assume a test file is discovered or exercised correctly without confirmation — verify via the runner configuration, or by checking that a deliberately broken assertion makes the test fail during test development. _[from `com.github.haexmas.atoms.coding-guideline-javascript-typescript/javascript-typescript-testing`, `com.github.haexmas.atoms.coding-guideline-python/python-testing`]_
- Do not mock the unit’s own logic, or the code under test, so heavily that the test only verifies the mock’s wiring or its own setup. _[from `com.github.haexmas.atoms.coding-guideline-javascript-typescript/javascript-typescript-testing`, `com.github.haexmas.atoms.coding-guideline-python/python-testing`]_
- Avoid clever metaprogramming when ordinary functions and classes suffice. _[from `com.github.haexmas.atoms.coding-guideline-python/python`]_
- Avoid expensive work, network access, and surprising side effects at module import time unless the project explicitly uses that pattern. _[from `com.github.haexmas.atoms.coding-guideline-python/python`]_
- Do not call blocking I/O or CPU-heavy work directly from an event loop, and do not call `asyncio.run()` from code that may already be running inside an event loop. _[from `com.github.haexmas.atoms.coding-guideline-python/python`]_
- Do not claim that formatter, linter, type-checker, or test checks passed without actually running them. _[from `com.github.haexmas.atoms.coding-guideline-python/python`]_
- Do not pass a growing collection of positional tuples or unrelated dictionary keys through the application; model the data explicitly instead. _[from `com.github.haexmas.atoms.coding-guideline-python/python`]_
- Do not use a bare `except`, catch `Exception` to hide a failure, or return `None` as an undocumented substitute for an error. _[from `com.github.haexmas.atoms.coding-guideline-python/python`]_

## MAY

- Existing projects may opt out of individual strict checks during migration, provided that choice is made explicit. _[from `com.github.haexmas.atoms.coding-guideline-javascript-typescript/javascript-typescript`]_
- A `.clone()` may be used when it expresses a real ownership boundary or is demonstrably the clearest and sufficiently cheap choice. _[from `com.github.haexmas.atoms.coding-guideline-rust/rust`]_
- `unwrap()` and `expect()` may be used when an invariant is local, explicit, and genuinely impossible to violate; document that invariant at the call site. _[from `com.github.haexmas.atoms.coding-guideline-rust/rust`]_
- Generated files, vendored code, snapshots, and other files not normally edited by hand may exceed the 500 LoC boundary, but should be excluded from this assessment. _[from `com.github.haexmas.atoms.general-coding/general-coding`]_
- Suspend the graphify-first authoring rule for the current session with any natural-language request to that effect, such as “skip graphify check” or “authoring rule off for this task”; the suspension applies only to the current session, must be re-issued in a new session, and does not exempt noting in the response which artifacts would have been flagged had the rule been active. _[from `com.github.haexmas.atoms.graphify-first-authoring/graphify-first-authoring`]_
